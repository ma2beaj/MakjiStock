### 3.2 데이터베이스 ERD

| ID | 이름 | 담을 내용 | 근거 코드 |
|---|---|---|---|
| E1 | 전체 ERD | 테이블 12개와 FK, 유니크 제약. 그룹: 시세(`products`, `daily_prices`, `trend_snapshots`, `fx_rates`) · 참여(`anonymous_visitors`, `price_locks`, `prediction_rounds`, `prediction_entries`) · 보상·운영(`reward_claims`, `job_runs`, `events`) · 인증(`cafe24_tokens`) | `supabase/schema.sql`, `supabase/migrations/001~007` |
| E2 | 이벤트 데이터 ERD (마케팅·분석용) | `events`와 `anonymous_visitors`·`products`·`prediction_rounds`의 관계, `source`(client/server/cafe24), PRD §21.3 퍼널 단계와 이벤트 이름 대응 | `supabase/schema.sql` `events`, PRD §21 |
| E3 | 고객 데이터 ERD (개인 정보 관리) | `anonymous_visitors`를 중심으로 `price_locks`·`prediction_entries`·`reward_claims` 연결. 컬럼마다 개인 정보 여부, 저장 방식(HMAC 해시, 암호화), 보관 위치(우리 DB와 Cafe24) 표시 | `supabase/schema.sql`, `lib/visitor.ts`, `lib/crypto.ts` |

E2·E3에는 **스키마와 구현의 차이**를 반드시 표시한다.

- `events` 테이블은 스키마에만 있고 앱 코드가 쓰지 않는다. 다이어그램에 "스키마만 존재(미수집)"로 표시한다.
- `anonymous_visitors`의 동의(`analytics_consent`)·UTM 컬럼도 코드에서 채우지 않는다.
- 이름·이메일·연락처 같은 개인 정보는 우리 DB에 없다. 방문자는 쿠키 원문이 아닌 HMAC 해시로만 식별하고, 회원·주문 정보는 Cafe24에 있다. E3는 이 경계를 한눈에 보여줘야 한다.

## 4. 작성 방식

- **형식:** Mermaid로 쓴다. GitHub에서 바로 보이고, 코드 리뷰로 변경 내용을 확인할 수 있다. ERD는 `erDiagram`, 시퀀스는 `sequenceDiagram`, 플로우차트는 `flowchart`, 상태 전이는 `stateDiagram-v2`를 쓴다.
- **위치:** 원본은 `docs/diagrams/`에 관점별 파일 4개로 둔다. 발표용 이미지가 필요하면 내보낸 PNG를 `assets/diagrams/`에 둔다.

  ```text
  docs/diagrams/
  ├── README.md            # 다이어그램 목록과 읽는 순서
  ├── 01-architecture.md   # A1~A3
  ├── 02-erd.md            # E1~E3
  ├── 03-sequences.md      # S1~S9
  └── 04-flowcharts.md     # F1~F5
  ```

- **다이어그램마다 붙일 것:** 한 줄 요약, 근거 코드 경로, 마지막으로 코드와 대조한 날짜.
- **읽는 순서:** A1 → A2 → E1 → F1 → S1 → S5·S6 → S2·S3·S4 → F2~F5 → E2·E3 → A3·S7~S9. 추상적인 전체 구조에서 시작해 사용자 기능, 자동 작업, 세부 규칙 순으로 내려간다.

## 6. 완료 기준

- 3절의 다이어그램 20개가 모두 `docs/diagrams/`에 있고 GitHub에서 렌더링된다.
- 모든 다이어그램의 테이블·컬럼·경로·시각이 코드와 일치한다. 특히 크론 시각은 `vercel.json`, 테이블은 `schema.sql`과 migrations를 합친 최종 상태와 대조한다.
- 구현되지 않은 부분(`events` 수집, 동의·UTM 저장, 주문 연동)은 "미구현"으로 표시되어 있다.
- 작성자가 아닌 사람이 코드와 한 번 더 대조해 검토한다.
